# ADR-0017：ISO 13485 过程包与受监管模块

- 状态：已接受（2026-10-15）
- 日期：2026-10-15
- 补充：ADR-0010（只用 ERPNext 一个底座；dee-qms 作方案库）、ADR-0011、ADR-0016（ISO 9001 过程包）

## 背景

ISO 9001 过程包（ADR-0016）已经跑通：过程包是数据，检查规则按记录判断，八张通用登记表补证据，差距报告、内审清单、
问卷与 AI 调整、按流程写程序文件都已上线。项目负责人的原则（2026-10-14）：**规则灵活设定，不把自己搞死；关键是程序通**。

第 2 期第 4 项是 ISO 13485（医疗器械质量管理体系）。它比 ISO 9001 要求更细：来料检验与抽样、合格供应商名录、文件控制与
培训确认、投诉与可报告性评估、校准、变更控制、风险管理、生产记录、追溯、发货与召回、管理评审。美国 FDA 的 QMSR
（21 CFR 820，2026-02-02 起施行）以引用方式采用 ISO 13485:2016，所以同一套模块也服务于美国的受监管企业（条款以原文为准）。

`eddiezgq/dee-qms`（Odoo 18，冻结）已经把这些做成 22 份方案（`docs/PLAN-*.md`）和约 6,900 行模型代码，原则与我们一致：
判定由确定性代码做、签字重输口令、签字后锁定、公司之间不同的东西是配置。ADR-0010 定了：它是方案库，
方案和测试是移植的规格书，纯计算逻辑可以改写过来，模型和界面重写。

## 决策

1. **ISO 13485 过程包和 ISO 9001 用同一套机制**：`wqops/hub/system/packs/iso13485.yaml`，过程、控制点、自写要求摘要、
   2016 版条款对照（项目负责人在 PR 里审核）、检查规则、设定、登记表。企业可以只采用其中一个标准，也可以两个都采用，
   共用同一批记录。不承诺认证、不进标准原文（ADR-0011）。
   实现（17a）：登记表定义移到共用的 `packs/registers.yaml`，加载时并入每个过程包（改登记表即两个包都出新版本，
   企业签字重新采用）；设置问卷移进各自的过程包（`questions:`，“否”对应的不适用控制点写在 `if_no:` 下）；
   每个标准的设定、不适用声明、证据链接、检查结果各自独立。ISO 13485 只允许第 6、7、8 章的要求声明不适用。
2. **先用现有模块和登记表跑起来，再按需把登记表换成专门模块**。第一步（17a）就让 ISO 13485 的大部分控制点能被判断：
   已有的 NCR、CAPA、资料库、来料检验、供应商事实比率，加上登记表（必要时加字段，如投诉的“是否需要向监管报告（人判断）”、
   培训的有效性评价）。后面的每一步把一块换成专门模块，登记表里的数据迁过去，控制点改为读专门模块。
3. **移植顺序**（每步一个 PR，做完汇报，等“继续”）：
   - **17a ISO 13485 过程包**：过程、控制点、条款对照、设定，基于现有模块与登记表。
   - **17b 来料检验与抽样**（`PLAN-IQC`、`PLAN-SEVERITY`）：抽样表（AQL、批量、n/Ac/Re，公司配置，标“已核对”）、
     检验计划（特性、限值，启用后冻结、出新版本）、按计划和批量确定样本量、逐项录入、确定性判定、签字；正常 / 加严 / 放宽
     转移由规则建议、人确认。结果写回 ERPNext 的 Quality Inspection（先起草、人确认，沿用 ADR-0008 的草稿方式）。
   - **17c 合格供应商名录**（`PLAN-ASL`）：供应商 × 物料的批准状态；未批准的采购草稿和来料检验给出拦截提示；
     ISO 9001 的供应商批准登记表数据迁过来。
   - **17d 文件控制与培训确认**（`PLAN-DOC`、`PLAN-TRAINING`）：在资料库上加定期复审、计划生效、文件生效后指定人员口令确认已读、
     逾期提示；培训登记表并入。
   - **17e 投诉**（`PLAN-COMPLAINT`）：投诉记录、调查、可报告性由人判断并签字（系统只提示时限和必答问题）、他人关闭。
   - **17f 校准**（`PLAN-CAL`）：设备台账、校准记录与签字、过期设备不能用于检验签字、失准影响追溯。
   - **17g 变更控制**（`PLAN-CHANGE`）与 **17h 风险管理**（`PLAN-RISK`，严重度 × 概率矩阵是公司配置，查表判定）。
   - **17i 生产记录、追溯、发货与召回**（`PLAN-DHR`、`PLAN-TRACE`、`PLAN-SHIP`、`PLAN-RECALL`）：**以 ERPNext 已有的批次、
     工单、发货单为准**，WenQuest Ops 只补受控的记录模板、逐步签字、放行、追溯查询和召回过程，不重复记 ERPNext 已有的数据。
   - **17j 管理评审输入汇总**（`PLAN-MR`）：各模块记录自动汇总、冻结快照，会议决定和签字记入管理评审登记表。
4. **从 dee-qms 移植什么**：方案文档作为规格；判定逻辑（抽样表查表、批判定、转移规则、风险矩阵查表、校准到期、追溯查询）
   改写为本项目的纯函数并保留其测试用例的意图；Odoo 的模型、视图、权限不搬。每步在 PR 里列出对应的 dee-qms 方案和改动。
5. **不变的原则**：判定只由确定性代码做（隔离检查）；签字重输口令；签字后锁定、作废写原因；留痕只增不改；职责分离；
   缺数据为“未知”；公司之间不同的东西（抽样表、AQL、矩阵、周期、编号、规则开关）是配置，可调，不写死。
6. **不做**：向 FDA 或其他监管机构提交报告（只记录人的判断和时限）；UDI 数据库对接；设计控制（ISO 13485 7.3）的专门模块
   （先用文件证据和登记表，以后另写 ADR）；软件验证（CSV）文档包。

## 项目负责人的决定（2026-10-15，“按建议”）

1. **移植顺序**：按 17a–17j 进行。
2. **生产、追溯、发货以 ERPNext 为准**：批次、工单、发货单用 ERPNext 的数据，不重复录入。
3. **来料检验在 WenQuest Ops 页面录入数值**：抽样、判定、签字在我们这里；结论起草回 ERPNext，由人确认。
4. **条款对照先做 ISO 13485:2016**；FDA QMSR 的额外要求以后单独补。

## 后果

- ISO 13485 一开始就能用（17a），不用等全部模块；之后每步都让一部分控制点从“登记表证据”升级为“专门模块的确定性判断”
- dee-qms 的方案和测试继续有用；工作量主要在重写界面和接上 ERPNext
- 范围大，按步交付，每步都要能单独上线、单独回滚
